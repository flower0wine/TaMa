# 任务

- spec\ui 下面是预期实现的 APP UI 图，但是有些功能实现起来可能有些困难，需要先进行深入调研和分析其实现的可行性。
- 将实施方案放在 spec\plan 目录下面，按照 UI 图，分析哪些功能实现不及预期，哪些功能是可实现的，用什么方式去实现是最合适的。
- 实施方案可以拆分为多个文件，聚焦各个页面，每个也可以拆分为不同的文件。
- 在编写对应的实施方案之前需要分析对应的 UI 图，图中的功能该怎么去实现，可以在网络上查找相应的解决方案。

# 代码规范

- 代码应易于维护、模块化且具有易读性。模块、文件等应遵守功能的单一职责原则，避免在同一个文件当中堆砌功能无关的代码。
- 项目文件结构设计需要有架构设计，目录命名具有前瞻性以及功能命名意义，避免无意义，含糊的文件或文件夹命名。
- 将通用代码进行封装，在合适的环节或时机使用设计模式来提高扩展性和可维护性。
- 在合适的时候可以使用设计模式来提高扩展性和代码可维护性，但是避免过度设计。

# 约束

- UI 统一且尽可能将组件复用，主题复用，尽量避免使用硬编码颜色值，采用 kotlin 推荐的方式。
- 对依赖的导入需要先去网络上核查再进行变更，无法断定的可以告知我。
- 对代码非常挑剔，你至少会分析并修改一至两遍，因为你相信好的代码是通过不断地迭代打造出来的。

# 注意

- 当遇到方向性问题时需要告知我，比如因为实现困难导致更改方向。但是一些文件命名不需要告知我。
- 目前处于开发阶段，不需要考虑应用的迁移或者是旧实现的兼容问题。
